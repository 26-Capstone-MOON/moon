# 경로 안내 파이프라인 알고리즘 문서

**MOON 프로젝트** — 랜드마크 기반 공간 기술 보행자 네비게이션 시스템

---

## 1. 개요

### 1.1 시스템 목표

MOON은 보행자 네비게이션에서 **화면 의존도를 줄이는 것**이 목표다. 지도를 없애는 것이 아니라, 지도 위에 공간 기술 안내·음성 TTS·촉각 피드백·파노라마 뷰 등 여러 채널을 겹쳐서 사용자가 화면을 보지 않고도 길을 찾을 수 있게 한다.

이를 위해 경로 위의 핵심 지점(Decision Point, DP)마다 주변 랜드마크를 선택하고, 그 랜드마크를 활용한 한국어 안내문을 자동 생성한다.

### 1.2 파이프라인 구조

경로 안내 파이프라인은 6단계로 구성된다:

```
STEP 1  경로 탐색 + DP 추출 (Tmap API)
  ↓
STEP 2  Virtual DP 삽입 (장거리 직진 구간 보완)
  ↓
STEP 3  후보 수집·병합 (Kakao Local API + OSM Overpass API)
  ↓
STEP 4  파노라마 요청 데이터 및 Vision cache 준비
  ↓
STEP 5  스코어링 + Vision V 반영 + 시퀀스 최적화
  ↓
STEP 6  안내문 생성
```

모든 알고리즘은 Python dp-pipeline 서비스에서 실행된다. Frontend는 결과를 받아 렌더링만 하고, Spring Boot는 요청을 중계만 한다.

## 2. 사전 지식

### 2.1 Haversine 공식 (대원 거리)

지구 표면 위 두 점 사이의 최단 거리를 구한다. WGS84 좌표계(위도·경도)를 입력받아 미터 단위 거리를 반환한다.

$$d = 2R \cdot \arctan2\!\left(\sqrt{a},\; \sqrt{1-a}\right)$$

$$a = \sin^2\!\left(\frac{\Delta\phi}{2}\right) + \cos\phi_1 \cdot \cos\phi_2 \cdot \sin^2\!\left(\frac{\Delta\lambda}{2}\right)$$

- $R = 6{,}371\,\text{km}$ (지구 평균 반지름)
- $\phi$: 위도(라디안), $\lambda$: 경도(라디안)

파이프라인 전반에서 사용된다 — DP 간 거리 계산, POI 거리 측정, Virtual DP 후보 간격 판별 등.

### 2.2 Initial Bearing (방위각)

출발점에서 도착점을 향한 방향을 북쪽 기준 시계 방향 각도($0°\sim360°$)로 구한다.

$$\theta = \text{atan2}\!\left(\sin\Delta\lambda \cdot \cos\phi_2,\;\; \cos\phi_1 \sin\phi_2 - \sin\phi_1 \cos\phi_2 \cos\Delta\lambda\right)$$

- $0°$ = 북, $90°$ = 동, $180°$ = 남, $270°$ = 서

사용처: POI의 좌/우 판별, 파노라마 촬영 각도 계산, 안내문의 방향 표현.

## 3. STEP 1: 경로 탐색 및 DP 추출

### 3.1 Tmap 보행자 경로 API

Tmap 보행자 API에 출발지·목적지 좌표를 보내면, GeoJSON FeatureCollection 형태의 응답이 온다. 이 응답은 **Point(안내점)와 LineString(경로 선분)이 교대로** 나타나는 구조다:

```
Point(출발) → LineString → Point(좌회전) → LineString → Point(횡단보도) → LineString → …
```

- **Point**: `turnType` 코드와 텍스트 안내(description)를 포함
- **LineString**: 보행자가 따라갈 좌표열과 구간 거리 정보를 포함

### 3.2 turnType → DpType 매핑

Tmap의 `turnType` 코드를 우리 시스템의 `DpType`으로 변환한다.

| turnType | 의미 | DpType |
|---|---|---|
| 200 | 출발지 | DEPARTURE |
| 12~19 | 회전 / U턴 | DIRECTION_CHANGE |
| 211~217 | 횡단보도 | CROSSWALK |
| 125, 126 | 고가도로, 지하도 | VERTICAL_MOVE |
| 127~129, 218 | 계단, 엘리베이터 | VERTICAL_MOVE |
| 201 | 목적지 | ARRIVAL |

**제외되는 turnType**: 1~7, 11 — 직진 구간으로, 별도 안내가 필요 없다.

### 3.3 DP 속성 계산

각 DP에 두 가지 핵심 속성을 계산한다.

#### distanceFromStart — 시작점으로부터의 누적 거리

경로 좌표를 따라 출발지부터 해당 DP까지 Haversine 거리를 누적 합산한다.

$$\text{distanceFromStart}_i = \sum_{j=0}^{i-1} \text{haversine}(P_j,\; P_{j+1})$$

**왜 Tmap의 거리를 쓰지 않고 직접 계산하는가?**

Tmap은 **모든** Point(제외된 turnType 포함) 사이의 구간 거리를 제공한다. 하지만 우리 시스템에서는 일부 turnType을 제외하므로, Tmap의 누적 거리와 우리 DP 사이의 거리가 일치하지 않는다. 또한 STEP 2에서 삽입하는 Virtual DP는 Tmap에 아예 존재하지 않으므로 Tmap 거리를 쓸 수 없다. 따라서 모든 DP(기존 + Virtual)의 일관된 거리 체계를 위해 직접 계산한다.

사용처: Virtual DP 삽입 판별(갭 > 200m), 진행률 표시, DP 정렬.

#### bearing — 진행 방위각

DP 위치에서의 진행 방향을 경로 좌표로부터 계산한다. DP 앞쪽 선분이 있으면 그 방향을, 없으면(목적지) 뒤쪽 선분 방향을 사용한다.

**왜 Tmap의 텍스트("우회전")를 쓰지 않고 직접 계산하는가?**

Tmap은 "우회전", "좌회전" 같은 텍스트만 제공하고, 수치 각도를 주지 않는다. 우리는 POI가 DP 기준 좌/우/정면 어디에 있는지 판별하기 위해 수치 각도가 필요하고, 파노라마 API의 pan 각도도 $[0°, 360°)$ 범위의 숫자여야 한다.

## 4. STEP 2: Virtual DP 삽입

### 4.1 필요성

Tmap에서 추출한 DP만으로는 긴 직진 구간에서 안내가 끊길 수 있다. 화면 없이 음성만으로 걷는 사용자가 "내가 맞게 가고 있나?" 확인할 수 없는 구간이 생기는 것이다. 이를 보완하기 위해 **연속 DP 간 거리가 200m를 넘으면** 중간에 확인용 DP(Virtual DP)를 삽입한다.

Virtual DP의 안내 유형은 위치 확인("국민은행이 보이면 잘 가고 있는 거예요!")이다.

### 4.2 삽입 알고리즘

**① 갭 탐지**: 연속 DP 쌍을 순회하며 `distanceFromStart` 차이가 200m을 초과하는 구간을 찾는다.

**② 후보 생성**: 해당 구간의 경로 LineString을 따라 **30m 고정 간격**으로 후보 지점을 생성한다. 경로 위의 정확한 좌표는 누적 거리 기준 선형 보간(interpolation)으로 구한다.

**③ 후보별 POI 스코어링**: 각 후보에서 Kakao POI와 OSM 공간 요소를 검색하고, $(P \times h \times U) \times D$로 점수를 매긴다.

**④ Greedy 선택**: 후보를 점수 내림차순으로 정렬한 뒤, 다음 조건을 만족하면 선택한다:
- 양쪽 경계 DP로부터 최소 90m 이상 떨어짐
- 이미 선택된 다른 Virtual DP와 최소 90m 이상 떨어짐

**⑤ Fallback**: 모든 후보의 점수가 0이면(POI가 하나도 없으면) 구간의 기하학적 중점에 1개를 강제 삽입한다. 이 경우 랜드마크 없이 기본 안내("계속 직진하세요")만 제공한다.

### 4.3 설계 근거

| 설계 | 근거 |
|---|---|
| 200m 임계값 | 한국 도시 블록 길이(100~150m) 감안. 1블록 이상 안내 없으면 불안감 발생 |
| 30m 후보 간격 | 너무 희소하면 좋은 POI를 놓치고, 너무 밀집하면 API 호출 과다 |
| 90m 최소 간격 | Virtual DP끼리 너무 가까우면 연속 안내가 오히려 혼란 |
| Greedy 선택 | 각 후보를 독립적으로 평가할 수 있어 구현이 단순하면서 실용적 |

## 5. STEP 3: 후보 수집·병합

### 5.1 적응형 반경 검색 (Adaptive Radius)

각 DP에서 Kakao Local API로 18개 카테고리(대형마트, 은행, 편의점, 카페 등)를 병렬 검색한다. 고정 반경이 아니라 결과 수에 따라 반경을 동적 조정한다:

```
초기 반경 50m로 검색
  → 결과 0개: 75m로 확대
  → 결과 20개 이상: 30m로 축소 후 재검색
  → 결과 1~19개: 현재 반경 유지
```

이 로직의 핵심은 **밀집 지역에서는 가까운 POI만, 한산한 지역에서는 넓게 탐색**하는 것이다. 강남역 앞에서 50m 반경으로 검색하면 수십 개가 나오지만, 주택가에서 50m로 검색하면 0개일 수 있다.

### 5.2 OSM 공간 요소 수집

DP 주변 80m에서 Overpass API로 `leisure=park` 공원, `place=square` 광장, `bridge=yes` 또는 `man_made=bridge` 교량·육교, `railway=subway_entrance` 지하철 출입구를 조회한다. node 좌표와 way/relation 중심 좌표를 사용하며, 실제 이름 또는 식별 가능한 ref가 있는 요소만 최대 30건까지 `source=OSM` 후보로 정규화한다. 지하철 출입구의 ref는 역명·name 계열 태그와 조합 가능한 경우에만 사용한다.

Kakao 후보와 OSM 후보는 이름·유형·근접 좌표를 기준으로 중복 제거한 뒤 같은 스코어링 흐름에 전달한다. Overpass 전체 요청은 2.5초로 제한하고, 오류·timeout·빈 응답이면 Kakao POI와 기존 Tmap 시설 후보만으로 계속 진행한다. 반복 조회는 DP 좌표 기반 120초 메모리 cache로 줄인다.

### 5.3 좌/우 판별 알고리즘

각 POI가 DP 기준으로 왼쪽·오른쪽·정면 어디에 있는지 판별한다.

1. DP → POI 방위각을 구한다 (Initial Bearing)
2. 진행 방향(DP의 bearing)과의 각도 차이를 계산한다

$$\text{angle\_diff} = (\text{POI 방위각} - \text{진행 방위각} + 360°) \mod 360°$$

3. 방향을 판정한다:

| angle_diff 범위 | 판정 |
|---|---|
| < 30° 또는 > 330° | **FRONT** (정면 ±30°) |
| 30° ~ 180° | **RIGHT** (우측) |
| 180° ~ 330° | **LEFT** (좌측) |

반대편 POI도 필터링하지 않고 방향 라벨만 부여한다. 예를 들어 진행 방향 기준 뒤쪽에 있는 POI도 LEFT/RIGHT로 분류되어 후보에 남는다 — 스코어링에서 거리(D)로 자연스럽게 걸러진다.

### 5.4 횡단보도 특수 처리

CROSSWALK DP에서는 **횡단보도 전후 두 지점**에서 POI를 검색한다:
- **before-crossing**: DP 위치 그대로
- **after-crossing**: DP에서 진행 방향으로 30m 앞 지점

이렇게 하면 "GS25 앞의 횡단보도를 건너서, 카페 방향으로 가세요" 같은 전후 맥락이 있는 안내가 가능하다.

### 5.5 동일 카테고리 수 (Uniqueness 기초)

각 POI 주변 100m 내에서 같은 `category_group_code`를 가진 POI가 몇 개인지 센다. 이 값은 STEP 5에서 Uniqueness(U) 점수의 기초 데이터가 된다.

## 6. STEP 4: 파노라마 요청 데이터 생성

각 DP에 대해 클라이언트가 Naver Panorama API를 호출할 때 필요한 좌표와 방향 정보를 생성한다. 서버에 저장된 Vision 결과가 있으면 후보 POI의 시각 점수, 외관 설명, 주변 환경 컨텍스트로 재사용한다. Vision 결과가 없으면 기존 POI·시설·OSM 기반 안내 흐름을 그대로 유지한다.

### 6.1 3방향 촬영

모든 DP에서 3방향 요청 데이터를 생성한다:

| 방향 | pan 계산 | 설명 |
|---|---|---|
| FRONT | bearing | 진행 방향 |
| LEFT | (bearing - 90° + 360°) mod 360° | 좌측 90° |
| RIGHT | (bearing + 90°) mod 360° | 우측 90° |

pan 값은 $[0°, 360°)$ 범위로 정규화한다.

### 6.2 isPrimary 결정

turnType에 따라 **Vision 모델이 주의를 집중할 방향**을 지정한다:

| turnType 그룹 | isPrimary 방향 | 이유 |
|---|---|---|
| 좌회전 (12, 16, 17, 212, 214, 215) | LEFT | 회전 후 보이는 방향 |
| 우회전 (13, 18, 19, 213, 216, 217) | RIGHT | 회전 후 보이는 방향 |
| 직진·수직·Virtual 등 나머지 | FRONT | 진행 방향 |

### 6.3 Vision 결과 병합

`POST /route/{routeId}/panorama-results`로 들어온 구조화된 Vision 결과는 `routeId + dpId + direction + candidate` 기준으로 route cache에 병합된다. 가능한 경우 같은 DP의 후보 점수, 선택 랜드마크, 안내문을 다시 계산한다. 경로 생성 전부터 사용할 수 있는 사전 결과는 DP 좌표·방향·후보 식별자 기준 cache로 조회한다.

## 7. STEP 5: 스코어링 모델

### 7.1 공식

각 DP에서 수집된 POI 중 가장 좋은 랜드마크를 선택하기 위한 점수를 계산한다.

$$S_{\text{final}} = \underbrace{(P \times h \times U)}_{\text{내재적 가치}} \times \underbrace{D}_{\text{공간 적합성}}$$

Vision 결과가 후보에 존재하면 아래 공식을 사용한다.

$$S_{\text{final}} = \underbrace{(P \times h \times U \times V)}_{\text{내재적 가치 + 시각 점수}} \times \underbrace{D}_{\text{공간 적합성}}$$

상점 후보의 `V`는 `color_distinctiveness × text_sign_ratio`, 건물 후보의 `V`는 `color_distinctiveness`로 계산한다. Vision 결과가 없거나 필요한 값이 없으면 기존 `(P × h × U) × D` 공식을 유지한다.

모든 요소가 **곱셈**으로 결합된다. 어느 하나라도 0에 가까우면 전체 점수가 크게 떨어지는 **게이팅(gating) 효과**가 있다. 예를 들어 아무리 유명한 은행이라도 영업 종료(h=0.5)이면서 100m 거리(D≈0)이면 점수가 거의 0이 된다.

### 7.2 P — 카테고리 인식도

보행자가 해당 카테고리의 건물을 얼마나 쉽게 인식하는지를 0~1 사이 값으로 나타낸다.

| 카테고리 | 코드 | P값 | 근거 |
|---|---|---|---|
| 대형마트 | MT1 | 1.0 | 큰 건물, 간판 눈에 잘 띔 |
| 공공기관 | PO3 | 0.95 | 시청·경찰서 등 랜드마크성 높음 |
| 은행 | BK9 | 0.9 | 일정한 외관, 간판 큼 |
| 병원 | HP8 | 0.88 | 십자 마크 등 식별 쉬움 |
| 학교 | SC4 | 0.85 | 대지 넓어 인식 쉬움 |
| 지하철역 | SW8 | 0.8 | 입구 표지 뚜렷 |
| 편의점 | CS2 | 0.7 | 작지만 24시간 조명 |
| 카페 | CE7 | 0.45 | 소규모 카페 많아 혼동 |
| 음식점 | FD6 | 0.4 | 개인 음식점 인식 어려움 |

**세부 분류 오버라이드**: 같은 은행(BK9)이라도 "저축은행"이나 "카드사"는 일반 시중은행보다 인식도가 낮으므로 P=0.45로 하향한다. 같은 마트(MT1)라도 "대형마트"는 1.0을 유지하고 소규모 마트는 0.8로 조정한다.

**프랜차이즈 보정**: 카페(CE7)와 음식점(FD6)은 기본 P가 낮지만, 스타벅스·맥도날드 같은 알려진 프랜차이즈는 인식도가 높으므로 P를 상향한다. 카페 프랜차이즈 14개(스타벅스, 투썸플레이스, 이디야 등), 음식점 프랜차이즈 17개(맥도날드, 버거킹, 롯데리아 등)가 등록되어 있다.

### 7.3 h — 영업시간 보정

Google Places API의 `isOpen()` 정보를 활용한다.

| 상태 | h | 근거 |
|---|---|---|
| 영업 중 | 1.0 | 간판 조명 켜져 있고, 사람 출입으로 인식 쉬움 |
| 영업 종료 | 0.5 | 외부 간판은 보이지만 어둡고 비활성 |
| 정보 없음 | 0.7 | 불확실성 반영 (보수적) |

### 7.4 U — 고유성

같은 카테고리의 경쟁 POI가 주변에 많을수록 "GS25 옆에서 우회전" 같은 안내가 모호해진다.

| 100m 내 동일 카테고리 수 | U | 의미 |
|---|---|---|
| 1 (유일) | 1.0 | 이 POI 하나만 있어 명확 |
| 2 | 0.7 | 약간의 혼동 가능 |
| 3 | 0.4 | 혼동 증가 |
| 4개 이상 | 0.2 | "편의점 옆"이라 하면 여러 개 |

### 7.5 D — 거리 적합성

DP에서 POI까지의 거리가 가까울수록 좋다.

$$D = 1 - \frac{d}{MD}$$

- $d$: DP에서 POI까지의 Haversine 거리 (m)
- $MD$: STEP 3에서 결정된 적응형 검색 반경 (30/50/75m)

$d = 0$이면 $D = 1.0$, $d = MD$이면 $D = 0.0$이다.

### 7.6 계산 예시

**상황**: 오후 3시, 검색 반경 100m인 DP에서 3개 POI를 평가한다.

**국민은행** — 30m 거리, 유일, 영업 중

$$\text{Intrinsic} = P \times h \times U = 0.9 \times 1.0 \times 1.0 = 0.9$$
$$D = 1 - 30/100 = 0.7$$
$$S = 0.9 \times 0.7 = \mathbf{0.630}$$

**GS25** — 20m 거리, 같은 편의점 3개, 영업 중

$$\text{Intrinsic} = 0.7 \times 1.0 \times 0.4 = 0.28$$
$$D = 1 - 20/100 = 0.8$$
$$S = 0.28 \times 0.8 = \mathbf{0.224}$$

**개인 음식점** — 50m 거리, 유일, 영업 종료

$$\text{Intrinsic} = 0.25 \times 0.5 \times 1.0 = 0.125$$
$$D = 1 - 50/100 = 0.5$$
$$S = 0.125 \times 0.5 = \mathbf{0.063}$$

**결과**: 국민은행(0.630) ≫ GS25(0.224) > 음식점(0.063) → **국민은행 선택**

GS25는 거리가 더 가깝지만, 주변에 같은 편의점이 3개여서 고유성(U=0.4)이 크게 깎인다. 국민은행은 거리가 조금 멀어도 유일하고(U=1.0) 영업 중이라 압도적으로 높다.

## 8. 시퀀스 최적화

스코어링으로 각 DP에서 최고 점수 랜드마크를 선택한 후, **경로 전체 맥락**에서 안내의 일관성을 점검하고 보정한다.

### 8.1 Phase 1: Forward Greedy 중복 제거

앞에서부터 연속 DP 쌍을 순회하며, 두 DP의 랜드마크가 **같은 이름**이거나 **같은 카테고리**이면 뒤쪽 DP의 랜드마크를 2순위 후보로 교체한다.

예를 들어 DP 3과 DP 4 모두 "GS25"가 1순위라면, 사용자는 "GS25에서 우회전 → GS25에서 좌회전"이라는 혼동스러운 안내를 받는다. 이를 방지하기 위해 DP 4의 랜드마크를 2순위(예: "올리브영")로 교체한다.

### 8.2 Phase 2: 방향 일관성 (지그재그 보정)

LEFT → RIGHT → LEFT 또는 RIGHT → LEFT → RIGHT 패턴이 나타나면, 중간 DP의 랜드마크를 양쪽과 같은 방향의 후보로 교체를 시도한다.

```
DP 1: 국민은행 (RIGHT, 0.95)
DP 2: GS25 (LEFT, 0.85)     ← 지그재그
DP 3: 올리브영 (RIGHT, 0.90)

DP 2의 후보 중 RIGHT에 있는 것:
  → 스타벅스 (RIGHT, 0.81) — 점수 하락 4.7%
```

점수 하락이 **20% 이내**(SWAP_SCORE_TOLERANCE = 0.20)이면 교체한다. 스타벅스(0.81)는 GS25(0.85) 대비 4.7% 하락이므로 교체 가능. 이렇게 하면 사용자가 "오른쪽 → 왼쪽 → 오른쪽"으로 시선을 왔다갔다 하지 않아도 된다.

교체 가능한 후보가 없거나, 점수 하락이 20%를 넘으면 원래 랜드마크를 유지한다.

### 8.3 복잡도

시간 복잡도 $O(n \times k)$. $n$은 DP 개수, $k$는 DP당 후보 수. 일반적인 도보 경로(DP 10~20개, 후보 5~10개)에서 100~200회 연산이므로 무시할 수 있는 수준이다.

## 9. STEP 6: 안내문 생성

### 9.1 작성 원칙

**대화체 사용**: "우회전하십시오"가 아닌 "우회전하세요". 딱딱한 명령어가 아닌 친근한 톤.

**거리 미터법 금지**: "50m 앞에서"가 아닌 "곧" 또는 "조금만 더 가면". 음성으로만 들을 때 "50미터"는 체감이 어렵다.

**한국어 조사 처리**: 마지막 글자의 받침 유무에 따라 "이/가", "을/를"을 자동 선택한다. 유니코드 한글 블록에서 `(코드 - 0xAC00) % 28 ≠ 0`이면 받침이 있다.

### 9.2 DP 유형별 안내 패턴

#### DEPARTURE (출발)
```
"안내를 시작합니다. 직진하세요."
```

#### ARRIVAL (도착)
```
"목적지 {이름}에 도착했습니다!"
```

#### DIRECTION_CHANGE (방향 변경) — 3단계 트리거

하나의 DP에 대해 2번의 안내가 발화된다:

**30m 전 (PRE_ALERT)**: 미리보기
```
"곧 오른쪽에 국민은행이 보일 거예요."        ← MATCHED/POI_ONLY
"곧 오른쪽으로 꺾이는 길이 나와요."           ← 랜드마크 없음
```

**10m 전 (ARRIVAL)**: 행동 지시
```
"국민은행을 끼고 우회전하세요."               ← MATCHED
"편의점 근처에서 우회전하세요."               ← POI_ONLY
"오른쪽으로 꺾으세요."                       ← 랜드마크 없음(fallback)
```

#### CROSSWALK (횡단보도)

before-crossing과 after-crossing 두 랜드마크를 활용한다:
```
"곧 GS25 앞의 횡단보도를 건널 거예요."       ← PRE_ALERT
"GS25 앞의 횡단보도를 건너서, 카페 방향으로 가세요."  ← PRIMARY
```

#### VERTICAL_MOVE (계단·엘리베이터)

시설 종류에 따라 고정 안내 + POI 위치 보조:
```
1순위 (POI 있음):  "GS25를 지나 바로 계단이 있어요. 올라가세요."
2순위 (Vision만):  "빨간 벽 끝에 계단이 있어요."
3순위 (아무것도):  "계단이 나와요. 올라가세요."
```

시설별 표현: 계단(올라가세요/내려가세요), 엘리베이터(엘리베이터를 타세요), 고가도로(육교를 건너세요), 지하도(지하보도로 내려가세요).

#### VIRTUAL (Virtual DP)
```
"국민은행이 보이면 잘 가고 있는 거예요. 계속 직진하세요."
```
